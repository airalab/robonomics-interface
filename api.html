Pallets¶

Datalog: a per-account ring buffer of timestamped records.

Each account has WindowSize (128) slots. DatalogIndex holds start and end: live records are at start, start+1, …, end-1 modulo the window, oldest first. When the buffer is full, start moves on, so at most WindowSize - 1 records are live; the slot at end may still hold an overwritten record and is not one of them.

class robonomicsinterface.pallets.SubmitOptions[source]¶

Options passed through to RobonomicsClient.submit().

Extrinsics¶

Calls, signed extrinsics, and what the chain says about them afterwards.

Everything here is offline: it takes a Runtime and produces bytes, or takes bytes from the chain and explains them. The client does the talking.

Signed extensions are read from the runtime metadata, in its order. Each one contributes an explicit part (sent in the extrinsic) and an implicit part (only signed); the values come from EXTENSION_VALUES. An extension this library does not know is fine if both its parts are empty, and an UnsupportedExtension otherwise — never a silently wrong signature.

Keys and addresses¶

ED25519 and sr25519 accounts: key derivation, signatures and message encryption.

ED25519 runs on PyNaCl, sr25519 on the [sr25519] extra (keys_sr25519). Wire formats match substrate-interface byte for byte: the same mini secret from a mnemonic, the same ed25519 → curve25519 conversion and the same NaCl box with the nonce in front. Reports already encrypted by the 2.x stack stay readable, and the ones produced here open with the old tools.

class robonomicsinterface.keys.Keypair[source]¶

An ED25519 or sr25519 account, with or without its secret key.

Build one with a from_* class method; crypto_type picks the kind (ED25519 by default, so an existing mnemonic keeps its address). A keypair built from a public key or an address can verify signatures and be encrypted to, but not sign or decrypt. The secret is held only inside the signing key: the mnemonic or URI it came from is not kept, and neither repr() nor exceptions ever show it.

Encrypt for one recipient.

BIP39 English mnemonics and the mini secret Substrate derives from them.

Substrate does not use the standard BIP39 seed. It derives a 32-byte “mini secret” from the mnemonic’s entropy, not from the mnemonic string, with PBKDF2-HMAC-SHA512 over 2048 rounds (substrate-bip39::seed_from_entropy). The standard seed would give a different address from the same words, which is why the tests pin this against vectors from substrate-interface.

Report envelope¶

The multi-recipient envelope: one symmetric key, wrapped for every recipient.

The payload is encrypted once with a random key for NaCl’s SecretBox, and that key is encrypted separately, with Keypair.encrypt_message(), for each address that may open it. The serialized form is the one already published by Robonomics Report Service:

{"data": "0x<secretbox>", "keys": {"<address>": "0x<box of the key>", ...}}

Optional metadata travels inside the encrypted payload as {"payload": <data>, "meta": {...}}; parse_decrypted() splits it.

A package has one key type, the sender’s: ED25519 senders wrap the key in NaCl boxes for ED25519 recipients, sr25519 senders in ECIES messages for sr25519 recipients. An address does not say which kind it is, so every recipient is taken to be of the sender’s kind; the recipient’s own key says how to open it.

Errors¶

Exceptions raised by the library.

Everything derives from RobonomicsError, so a caller can catch the library as a whole. Input errors also derive from ValueError: they describe bad data, and retrying them is pointless.

Messages never contain secrets: no mnemonic, seed or private key is ever formatted into an exception, including the input that failed to parse.
